Dear friends, hello and welcome. In the previous lessons, if you remember, we talked about the architecture of Databricks. Specifically, the relationship between the control plane and the compute plane. In that lesson, we saw the big picture. The user interface and management tasks were in the control plane, while the actual computations were carried out in the compute plane. We also briefly introduced the options within the compute plane, such as classic compute and serverless compute. In other words, in the architecture lesson, we explained where the work happens. In this lesson, however, we are narrowing our focus. We'll only talk about compute. We will go into detail about which types of compute options exist in Databricks, what purposes they serve, and most importantly, which one we should choose in different scenarios. So, to summarize. In the architecture lesson, we answered the question, where? While in this lesson, we will answer the question, which one? First, let's recall the concept of compute. Compute essentially means a cluster. A cluster is made up of virtual machines. A machine called the driver node plans the jobs while the worker nodes execute them. That's why you might hear the terms compute and cluster used interchangeably. They both mean the same thing. In Databricks, we can think of compute options under two main categories, classic compute and serverless compute. Let's review them again, since this is important enough to appear in an exam. Classic compute is a model that runs entirely within your own cloud account. If you are using Azure, the machines are launched in your Azure subscription. If you are on AWS, they are launched in your AWS account. This model gives you full control. You decide which machine sides to use, which runtime version to run, and which libraries to install. However, startup time can be long, and as long as the cluster is running, it generates costs. Serverless compute, on the other hand, is fully managed by Databricks. When you request a cluster, the machines are ready within seconds. Thanks to auto scaling, they automatically grow or shrink based on your workload, and you don't need to manage anything. This option is especially useful for quick starts, short analyses, or running SQL queries through BI tools. Now let's dive a little deeper. Within classic compute, there are two types. Let's explain this with a real life example. Imagine you're cooking in your kitchen at home. The stove is always on, the pot is sitting there, and you can start cooking whenever you want. This is similar to an all-purpose cluster. While you are coding, cleaning data, or experimenting with new libraries, it's always ready. But keep in mind, the stove keeps burning until you turn it off. In other words, it constantly consumes energy, which translates into cost. The all-purpose cluster works the same way. It keeps running until you shut it down, continuously generating costs. Now let's also think about the job cluster. This time, let's use a restaurant analogy. When you place an order at a restaurant, the kitchen starts working, your meal is prepared, and served to you. Once the job is done, the kitchen closes, and the lights go off. That's exactly how a job cluster works. For example, if you have an ETL job that runs every night at 2 a.m., the cluster starts when the job begins, does its work, and shuts down immediately after finishing. Since it doesn't stay idle, the cost is much lower. However, if you want to use it again, the same cluster won't come back. A new job will spin up a new cluster. Now that we understand the cluster types, let's move on to some important features. Friends, there is a feature called pools. Think of it like a parking lot, where a few cars are always running with their engines warmed up. Normally, it takes a few minutes to get your own car out of the garage and warm it up, but the cars in the pool are ready. You just hop in and drive. In Databricks, pools work the same way. Clusters are pre-warmed, and startup time is greatly reduced. This provides both time and cost advantages, especially for teams that frequently start and stop clusters. Now let's talk about another compute option, SQL Warehouse. Think of this like a library. Inside, there are only books, and your only task is to read. You can't cook complex meals or repair engines here. You only read. SQL Warehouse is fully optimized for SQL workloads. It is ideal for connecting tools like Power BI or Hublow. It runs SQL queries very fast, but you cannot use it to run Spark code. So when should we use all these options? If you say, I wanna start quickly, I don't wanna wait, then serverless compute is the right choice for you. If you say, I write code, I need to install custom libraries, and I need an environment that is always on, then the all-purpose cluster is your friend. If you say, my job runs at certain times on a regular schedule and then shuts down, then the job cluster is ideal for you. If you say, I only write SQL, I generate reports, I'm an analyst, then SQL Warehouse is just right for you. And finally, if you say, I have to use a classic cluster, but the startup time is too long, that's where pools come in. As you can see in the architecture lesson, we previously drew the big picture, where the control plane is, where the compute is, where the storage is. Now with this lesson, we have gone deeper into the compute options. You've learned which compute type should be preferred in which scenario.
