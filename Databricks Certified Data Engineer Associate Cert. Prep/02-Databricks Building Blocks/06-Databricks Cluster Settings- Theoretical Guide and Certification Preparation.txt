Hello dear friends. In this lesson we will talk about Databricks cluster configuration settings. First we need to understand this the free edition version we are currently using does not give us the chance to see all these settings in practice. But this is not something discouraging because in the Databricks certification exam and in real projects the real question you will face is which setting should I choose and when. In other words you are not expected to play with every part hands-on but you do need to know what each part does. That's why we will cover this lesson entirely in theory and this knowledge will be more than enough for the exam. Some of you might ask what exactly is a cluster? Let's clarify this concept first. Compute and cluster actually mean the same thing but we use different words depending on the context. When we say compute we refer generally to computing power, meaning the virtual machines running in the background. When we say cluster we emphasize how that computing power is organized. Think of it like this. Compute equals the engine itself, its power, horsepower. Cluster equals the type of vehicle carrying that engine, how many seats it has, and how the driver and passengers are arranged. That's why Databricks uses these terms interchangeably because when you create a compute environment you are essentially creating a cluster. But when we say cluster configuration Databricks allows you to adjust the detailed settings of the compute. Now that we've separated the compute and cluster concepts let's move on to how we can configure this cluster. So imagine we have a vehicle with its engine running. Do we want to make it a single seater car or turn it into a bus? Who will we put inside? Which engine will we choose? And how long do we want it to run? Cluster configuration gives us the ability to answer all these questions. First setting we will look at is whether it will be single node or multi-node. This is one of the fundamental settings that determines the capacity of the compute and which workloads it is suitable for. Here you can think of a node as a worker. In a single node cluster there is only one worker and this worker is both the foreman and the laborer. That means it both gives the orders and does the work itself. This is sufficient for small and simple tasks. For example a small data analysis or a quick prototype project is ideal. A multi-node cluster on the other hand consists of one foreman, driver, and many workers under them. The foreman distributes the tasks, each worker does their own part, and the job finishes much faster. That's why multi-node clusters are necessary for large ETL processes or large-scale data processing scenarios. Think of it like this. One painter may be enough to paint a small apartment, but to paint a stadium you need dozens of workers. Now let's look at access mode. The next setting is access modes. Here Databricks offers us three options, single user, shared access, and no isolation share. Single user. In this mode the cluster can only be used by one person. Think of it like your personal computer. Nobody else is on it and you have all the permissions. It supports all languages, Python, SQL, Scala, R, and is completely suitable for personal tasks. Shared access. This mode is similar to a shared office space. Multiple users can work on the same cluster, but everyone has their own desk, files, and cabinet. In other words, tasks don't get mixed up and there is security. This mode is especially preferred in corporate environments. It requires a premium workspace and supports Python, SQL, and in some cases Scala. No isolation shared. This, however, is a bit more risky. Shared environment. Think of it like an office where desks aren't separated. One person's files may mix with another's. There is no isolation, meaning if one user consumes too many resources it can disrupt the work of others. It is usable in many cases, but it is not recommended for production environments. Now let's move on to Databricks Runtime. You can think of this as the engine of the vehicle. Databricks Runtime is an optimized version of Spark along with bundled libraries. If you're only doing general data processing, the standard runtime is sufficient. But if you are working on machine learning, you would choose Databricks Runtime ML. This is like adding extra turbo parts to your engine. Libraries like TensorFlow, PyTorch, Keras, and XGBoost come pre-installed. There is also a special accelerator option here called Photon. Enabling Photon is like adding a turbocharger to your engine. Spark queries run much faster. This makes a significant difference, especially in big data workloads. Now we come to an important cost patrol feature, auto termination. Let's say you start a cluster and finish your work but forget to shut it down. In this case, the cluster stays on unnecessarily and adds to your bill. With auto termination, if a cluster is unused for a set period, it shuts down automatically. It's like having a smart system that turns off the lights for you if you forget to switch them off when leaving the house. The default time is 120 minutes, but you can set it to anything from 10 minutes to one day. This feature is critical for protecting both your personal budget and the company's budget in corporate projects. So dear friends, I believe the topic is now clearly understood. As I mentioned at the beginning of the lesson, since the free edition gives us a ready-to-use compute environment, we cannot adjust these settings ourselves. However, since they can appear in the certification exam, we have reviewed them theoretically. In short, you may have seen the create compute screen in some cases. In the free edition we're using, this is not available because only serverless warehouse is provided. But if we had a paid Databricks workspace, from that screen we would be able to create either an all-purpose cluster or a job cluster. For the certification exam, just knowing this screen is enough.
