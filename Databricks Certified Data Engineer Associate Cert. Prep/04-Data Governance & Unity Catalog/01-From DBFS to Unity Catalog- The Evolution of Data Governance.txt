Lecture: From DBFS to Unity Catalog: The Evolution of Data Governance

Dear friends, hello everyone. In this lesson, we will start a new chapter and learn how data is managed in Databricks. Yes, if we think of Databricks as a data platform, its core job is to store data, provide access to it, and manage it securely. But this is not as simple as it sounds. Data can come in many formats, CSV, JSON, images, videos. Some we keep as files while others we want to convert into tables and query with SQL. In other words, there are two different worlds, the file world and the table world. In the early years of Databricks, there were two separate systems to manage these two worlds, DBFS, Databricks File System, and Hive Metastore. Let's now understand these two concepts before moving forward. DBFS, a single window for files. Friends, DBFS is essentially an interface built on top of cloud storages. ADLS in Azure, S3 in AWS, GCS in Google. Normally, accessing these cloud storages can be complicated, but DBFS makes them appear as if they were just a shared folder on your computer. This way, you can directly see, read, and write files. How does cloud storage actually work? Normally, data resides in cloud storages like Azure Data Lake Storage, ADLS, Amazon S3, or Google Cloud Storage, GCS. To access these, you usually need long URLs, access keys, and API calls. In short, reaching a file can be quite complex. So how does DBFS simplify this? DBFS places a middle layer on top of these cloud storages. This layer makes the files appear as if they were on your local disk in a shared folder. For example, normally, to access a file in Azure, you might need a path like this, abfss://container.account.dfs.core. windows.net/.path/.to/.file.csv. With DBFS, you can access the same file like this, dbfs://mnt/.mydata/.file.csv. As you can see, DBFS provides a simpler path. The file still resides in the cloud, but you can access it as if it were on your local disk. Hive Metastore turning files into table. On the other hand, working directly with raw files is not always practical. With a CSV file, unless you define things like this column is X, this data type is integer, this one is date, it's difficult to query it with SQL. That's where Hive Metastore came in. Hive Metastore allowed you to register data as a table. For example, if you define the CSV files in a folder as a sales table, the Metastore records the table name, column names, and data types. Then when you run select asterisk from sales, the system actually reads the files in the background, but you interact with them as if they were a table. You can think of this like a library catalog. There may be hundreds of books on the shelves, but with the catalog, you know where each book is. Hive Metastore worked like a catalog for data. In summary, DBFS managed the files, Hive Metastore managed the tables. It's like one ledger keeping track of inventory while the other tracked accounting. In the beginning, this setup was fine, but over time as company needs grew, it became insufficient. Yes, did you notice? Over time systems automatically evolved. As time went on, it was no longer enough to grant permissions just at the table level. New requirements emerged such as hide this column or only certain users should see this row. It also became necessary to answer the question who accessed which data and when. In other words, auditing became mandatory. Companies wanted to enforce the same governance rules across different cloud environments. Azure, AWS, GCP. There was also a need for lineage, showing where data came from and where it went. But DBFS and Hive Metastore fell short in these areas. They were two separate systems and did not provide a unified solution. That's why Unity Catalog was developed. Unity Catalog brought together the roles of DBFS and Hive Metastore under one umbrella. Now both files and tables are governed by the same system. Along with this, many modern features were introduced. Row and column level access control, for example, masking a customer's personal ID number. Audit logs, who read which table and when. Data lineage, trace data from its source all the way to reports. Multi-cloud and multi-workspace support. One policy, multiple environments. You can think of Unity Catalog as moving all of a company's ledgers into a single centralized accounting system. Now, everyone works in the same system and it's possible to see at a glance where data is and who is using it. Friends, Unity Catalog doesn't just centralize, it also organizes data with a clear hierarchy. You can compare this structure to the governance system of a country or the organizational structure of a university. Let's briefly look at this hierarchy. Metastore, the top layer, the registry of all catalogs, schemas, and tables. Think of it like a national population registry. Catalog sits under the metastore, represents large business units or environments, for example, a finance catalog or a retail catalog. This is like the faculties in a university. Schema lives inside a catalog, smaller subdivisions. For instance, within the finance catalog, you might have an accounts schema or a payroll schema. This is like the departments under each faculty. Tables, views, functions, volume. This is the lowest layer where the actual data objects reside. Table equals structured data like an Excel sheet. View equals filtered or aggregated versions of tables. Function equals small utilities that store reusable calculation logic. Volume equals dedicated storage for files, CSV, JSON images, et cetera. It's very helpful to think of this structure as similar to a university chain. Faculty, department, course, course material. Yes, we will dive deeper into this hierarchy in the upcoming lessons, but let's continue for now. Friends, as you remember, in the medallion architecture, data improved in quality as it moved through the bronze, silver, gold layers. Unity Catalog is the ideal system to organize these layers. Now, here's the problem. These layers are great, but how will a data engineer or analyst know which folder contains which table when they want to access the data? Now, how do we ensure security? That's where Unity Catalog comes in. It places the layers into a clear hierarchy. It lets you control permissions at the layer level. It shows data lineage, which table in bronze transformed into which table in silver and which columns were used in the gold report. Let's say we were working on a retail project. Using the Unity Catalog hierarchy, we define prod.retail underscore bronze, raw data. Example, sales receipts from cash registers, unfiltered. Prod.retail underscore silver, cleaned data. Example, missing customer IDs filled in, date formats standardized. Prod.retail underscore gold, report-ready data. Example, daily sales revenue, top seller products, KPIs. Here, the prod part can represent a catalog at the top level of Unity Catalog. In other words, prod equals the production environment. Underneath, schemas define the bronze slash silver slash gold separation. So what happens? Medallion architecture gives you a data processing flow from raw to business intelligence. Unity Catalog organizes this flow like an organizational chart. Who sees what and where each table came from. This way, it's not just about processing data, but also about delivering it securely in a traceable and organized way. All right, friends, I think the topic is clear. We'll end the lesson here.
