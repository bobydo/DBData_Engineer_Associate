Dear friends, hello everyone. In the previous lesson, we saw the basic structure of Unity Catalog and touched on it briefly. Do you remember what I said? I told you, we will explore this topic in more detail in a later lesson. Well, here we are now. In this lesson, we'll examine the layers of Unity Catalog. Let's get started. So what did these layers look like in general? At the very top, we had the Metastore, beneath it the Catalog, then the Schema, and at the bottom the Tables, Views, Functions, and Volumes. Yes, in this lesson, we'll take a closer look at each part of this structure. Let's begin. Metastore. The top-level roof. The Metastore acts as Unity Catalog's largest ledger or archive. It stores the record of all catalogs, schemas, and tables. But here's a critical difference. Don't confuse it with the Hive Metastore. In the past, Hive Metastore operated at the workspace level, meaning each workspace had its own separate ledger. Unity Catalog's Metastore, however, operates at the account level. That means you can bring together data from all your workspaces under one roof. We can compare this to a country's Central Population Registry system. In the past, each town kept its own ledger, but now there's a single centralized system. That's why workspaces are no longer isolated from one another. They can all be connected to the same Metastore. Catalog, a new layer. Under the Metastore comes the Catalog, a new concept introduced with Unity Catalog. Hive Metastore did not have this concept. You can think of a catalog as the departments of a large company. For example, one catalog could be finance, another sales, and another HR. Or you could separate them by project environment such as dev, test, and prod. Thanks to catalogs, you can keep data organized by business unit or environment. It's like creating sections within the ledger. Schema the structure under the catalog. Next is the schema, which sits under the catalog. You can map the schema to the database concept in traditional databases. But here's the important note. We are encouraged to use the term schema instead of database. Why? Because the word database can be misleading, making it sound like a completely separate database system. In reality, it's simply a folder-like structure used to group data. Think of it as the relationship in a university. Faculty equals catalog, department equals schema, tables the most common objects. Friends, under the schema, the most commonly used object is the table. Tables are structured data, objects made up of rows and columns. But there are two types of tables, managed and external. Let's briefly touch on them now, and we'll go deeper later. Managed table means Databricks has full control over the data. Both the data itself, files, and the metadata, table definition, column details, et cetera, are stored by Databricks. If you delete the table, not only the definition, but also the underlying files are removed from the cloud. In other words, Databricks owns the data. In an external table, Databricks only stores the metadata, in other words, the identity card of the table. The actual data files remains with the cloud provider. When you delete the table, Databricks removes only the identity card. The actual files stored in the cloud remain untouched. This model is especially useful when consuming data written by other systems. For example, you can define and use as a table in Databricks, the files created by Azure Data Factory or Fivetran. The key difference, managed table equals, Databricks is both the owner and the manager of the data. If you delete it, the files are deleted as well. External table equals, Databricks only keeps the metadata. If you delete it, only the metadata record is removed. The files remain. This distinction is especially important. If you want to produce and manage data directly in Databricks, a managed table makes sense. If you want to use data produced by other systems inside Databricks, an external table is more suitable, as I mentioned. We'll dive into these two table types in more detail in another lesson. For now, this much is enough. Let's move on. Besides tables, Unity Catalog also introduces a new object, volume. Volumes are mainly used to store unstructured files, such as images, JSON files, log records, etc. You can think of this as a storage room. On your desk, you keep documents, tables, but boxes full of files, volumes are stored in the storage room. Thanks to the catalog, you can securely access those files whenever needed. Now, inside a schema, you don't just have tables and volumes. There are also views and functions. View a virtual table derived from existing tables. For example, you can filter only the last 30 days from a sales table and create a view. Function allows you to package and store frequently repeated calculations. For instance, instead of writing the same date conversion logic every time, you define a function. These are helpful tools that make your work life much easier. All right, we've understood these topics. Now let me share an anecdote. There's one more important point. With the arrival of Unity Catalog, Hive Metastore didn't completely disappear. Databricks provides backward compatibility. In every workspace, there is still a built-in pseudo-catalog called hive underscore metastore. You can continue creating tables there out of habit. However, for new projects, the recommended approach is to use Unity Catalog. Because Hive Metastore lacks modern features such as column-level access control, audit logs, and lineage. Friends, I will demonstrate this in practice, but let me explain it theoretically as well. With Unity Catalog, when accessing a table, you now need to use three-level naming in the format. Catalog dot schema dot table. For example, finance dot sales dot customers. Here, finance, catalog, sales, schema, customers, table. In Hive Metastore, sometimes two levels, schema dot table, were enough. But with Unity Catalog, we get a clearer, more structured, and more secure approach. To summarize, in this lesson, we explored Unity Catalog's hierarchy in more detail. Metastore works as an account-level umbrella. Catalog is a new concept introduced with Unity Catalog. Schema is preferred, instead of the old-term database. Tables can be either managed or external. Volumes are used for storing files. Views and functions are helpful supporting tools. Hive Metastore still exists, but with limited functionality. We now access data using a three-level naming structure. This way, we've clarified the details behind the bigger picture we saw in the previous lesson. We'll continue from here in the next lesson. See you soon. Take care.
