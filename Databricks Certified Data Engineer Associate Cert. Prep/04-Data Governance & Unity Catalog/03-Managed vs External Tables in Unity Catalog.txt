A managed table means that Databricks manages both the identity of the data, metadata, and the data itself, files. When we think of a table, we are actually talking about two separate things. The data itself, which are the files that contain the records, row by row for example, values like joseph-25-stockhole, and the identity of the data, meaning the metadata that describes it, the table name, which columns it has, the data types of those columns, and in which schema and catalog it resides. You can think of metadata like an ID card. The card doesn't contain the person themselves, but it holds descriptive information such as their name, date of birth, and ID number. In Databricks, if you are using a managed table, both the metadata and the actual data are managed by Databricks. When you drop the table, both the identity and the content disappear together. An external table, on the other hand, is a model where Databricks only keeps the ID card, metadata. The files themselves remain in an external location and are often shared with other systems as well. Here, Databricks acts like a tenant when you turn off the lights and leave drop. The house itself remains, the table definition is deleted, but the files stay untouched. That's why external tables are ideal when you want to simply register and use data in Databricks that was written by external systems like ADF or Fivetran. So where do we make this choice? Friends, the decision about what kind of table it will be is made at the moment you create the table. Under unity catalog, if you create a table with create table without specifying a location, it becomes managed because Databricks writes the data into its own default managed location. If you provide an explicit folder path with location, dot, dot, dot, then the table becomes external. The metadata is stored in UC while the files remain in the cloud path you pointed to. So the practical intuition is no location equals managed. Specify a location equals external and unity catalog managed tables are always Delta format. You cannot create managed tables in parquet slash CSV slash Jason. For those formats, you must use an external table. Yes, in managed tables, the life cycle is fully controlled by Databricks end to end schema evolution. Maintenance operations like optimize slash Z order, vacuum and retention policies are all centrally managed. When you drop the table, the files are also deleted. In other words, the cleaning crew is included in the same contract. For external tables, Databricks acts only as a registry clerk, it updates the table definition and runs performance optimizations. But you are responsible for the physical lifecycle of the files. Even if you drop the table, you still need to delete the file separately on the cloud. This difference is similar to asking, are all the construction and maintenance jobs handled by a single contractor, or are they shared with the building owner? Both table types benefit from unity catalogs are back column masking audit and lineage features. We'll explore these both theoretically and practically. Bronze, raw data ingested from the source into a table, often external because the files already come from an external source. For example, IOT system or ETL tool. External tables facilitate data sharing across platforms. For example, when the same files are read by Databricks and an MPP warehouse, because you connect to a shared cloud folder via a contracted access model IM slash ACL. Managed tables, on the other hand, simplify sharing within Databricks via delta sharing or secure views. It's like one-click sharing for internal teams. In short, external enhances cross-platform sharing while managed enhances internal simple sharing. Two critical warnings to remember. If you drop a managed table, the files are deleted as well. This is a conscious irreversible choice. Do not directly delete or manipulate files in the folder behind an external table. In a delta table, all changes must go through delta commands. Otherwise, the transaction log and data files will become inconsistent and the table will lose integrity. This is like taking money from a cash register without updating the ledger. The records won't match. Friends, sometimes you may want to convert an external delta table into a managed table, for example, to simplify maintenance. The usual way to do this, if it's delta, is to copy it into a managed location using methods like deep clone or CTAS, create table as select. The reverse, managed external, involves writing the data to an external target and creating a new external table. The main idea, instead of changing the table type like a label, it's cleaner to recreate the data according to the rules of the target type. Practical compass when deciding. If you produce data inside Databricks and want to manage it centrally, silver slash gold layers, frequent maintenance, frequent merge slash optimize, centralized governance, clear lifecycle, stick with managed tables. It's like having a single contractor managing a well-organized site. If data will be produced or consumed by other systems, storage is managed by a separate account slash team, and you want the file lifecycle to stay there, choose an external table. Think of it like a shared space on a shared campus. Both approaches are valid. You are deciding where ownership should reside. In short, managed VS external is not just a technical detail. It's an operational strategy. Managed tables provide a world where Databricks is the homeowner. External tables provide a world where Databricks is the tenant. In a medallion journey, most organizations operate with minimal friction by keeping raw data external and processed slash value added layers managed. This way, you leverage Delta's ACID guarantees while managing your data consistently, securely, and traceably through Unity Catalog's governance framework.
