During the streaming process, how does Spark know where it left off, and how can it continue from the same point if a problem occurs? Dear friends, the answer to this question lies in the checkpoint mechanism, which I'll take you through in the theory lesson. You can think of the checkpoint in its simplest form as Spark's memory. Streaming jobs, unlike batch jobs, don't just run once and finish. I've probably repeated this a hundred times. It represents a continuously flowing process over time. That's why Spark always needs to know this. Which data have I already processed and which are still waiting? My dear friends, the checkpoint is the specific location where Spark persistently stores all of this critical information. The moment we specify the checkpoint location parameter in our code, we're basically telling Spark, write everything related to this streaming job here and remember it from here when needed. Yes. At this point, we can think of a metaphor, dear friends. Let's use a metaphor. Think of the streaming process like a package distribution center. An incoming file gets packaged. The streaming job is an automated system that processes this package, and the Delta table is the warehouse where the packages are delivered. The checkpoint, on the other hand, is the official logbook kept by this center. This logbook records which packages have been received, which ones have been placed in the warehouse, and which ones are still on the way. Spark keeps this logbook in the checkpoint directory, and checks these records before every new operation. Every time a streaming job runs, Spark first goes to the checkpoint directory and asks, have I started this job before? If the checkpoint directory exists, Spark looks at the information there to understand which data was last processed successfully. If there is no checkpoint, Spark starts the streaming process from the very beginning. That's why the location of the checkpoint must be unique for each streaming job. Using the same checkpoint for two different streaming jobs is like two different distribution centers trying to write in the same logbook. This leads to serious confusion. There's a very important reflex in Spark's operating model, folks. First, take notes, then start working. When Spark starts a micro-batch, it writes to the checkpoint which data it will process in that batch. This is like a teacher taking attendance before starting an exam. In other words, Spark makes a note to itself. I'll process the data in this range. Friends, this approach is critically important to prevent data loss in unexpected error scenarios. Now, let's consider an even more critical scenario. The streaming job is running, data is being processed, and right at that moment, the system stops or the job fails. When Spark comes back up, it checks the checkpoint, folks. If Spark sees a record in the checkpoint indicating that the previous operation was completed, it continues with the next data. However, if it only sees a record that the operation was started and there is no record of completion, Spark will reprocess that data. At first glance, this behavior might seem risky. But in fact, this is exactly what forms the foundation of reliability in streaming. For Spark, the worst-case scenario is not processing the data at all. If necessary, reprocessing the data is always safer. This is where the importance of working with Delta Lake becomes clear. Dear friends, you can think of Delta Lake as a smart attendant in a warehouse. If the same package arrives twice, it recognizes the duplicate and keeps the process running smoothly without any disruption. So even if Spark processes the same data again, Delta Lake prevents the table from being corrupted or from creating uncontrolled duplicates. This high level of compatibility makes Spark-structured streamings exactly once guarantee, both practically applicable in real-world scenarios and consistently achievable for developers. Friends, it's also important to remind you of this in this lesson. We worked in the free edition environment and added the data manually. We ran the streaming with the available now trigger. This tells Spark, process everything that has come in so far, then stop. However, this approach doesn't change the logic of streaming. Checkpointing is still maintained. Spark still knows which data has been processed and doesn't reprocess the same files if the job is run again. So we actually simulated a real-life automatic streaming scenario in a controlled and educational way. If there were no checkpoint, Spark would have to re-read everything from the beginning every time it runs. This would mean the same data would be written over and over again, leading to incorrect results and unreliable pipelines. That's why we can say this very clearly, without a checkpoint, streaming is not acceptable in a production environment. The checkpoint is the most important aspect of Spark-structured streamings reliability and plays an indispensable role in large-scale data projects. However, the longer the job runs and the more micro-batches are processed, the number and content of the subfiles grow over time. All right, now let's start with the metadata folder first. Which query do I belong to? Dear friends, you can think of this as the ID card of a streaming job. Thanks to this information, when the job is restarted, Spark understands that it's the same streaming job and doesn't treat it as a brand new job starting from scratch. Yes, right here is the source folder. It represents the reading side of the streaming job. Here, depending on the source, Spark keeps track of which files or which data ranges have been read. Since, in your example, this is a file-based ingestion, Spark manages the following information in this folder. Which files have I seen before and which ones are new? Guys, in other words, the source folder is like the eyes of the streaming process. It records what Spark detects in the outside world. Let's continue. Look, there's an offsets folder. It's one of the most critical parts of the streaming checkpoint structure. Before each micro-batch starts, Spark writes a record here like this. In this batch, I will process the data from this point to that point. Since this record is written before the batch actually starts, it acts like a preliminary note. Even if Spark hasn't written any data yet, it leaves this message in the offsets folder. These are the records I'm targeting. So, if the job stops halfway, Spark knows which data was planned to be processed. Look, we have a folder called commits. This complements the offsets. When a micro-batch completes, Spark writes a record to the commits folder. This record means this batch was processed successfully and the results were written to the target. Guys, when Spark restarts, it reads both the offsets and commits folders together to make a decision. If there is an offsets record for a batch but no commit record, it means this batch was interrupted and will be processed again. If both records exist, Spark safely continues with the next data. In summary, these folders in the checkpoint directory make up Spark's memory layer. Metadata represents the identity of the job. Sources represent the reading side. Offsets represent the planned work. Commits represent the work that has been successfully completed. Guys, this structure is always created with the same logic. The only thing that changes is the number of files inside. The longer the streaming job runs and the more micro-batches it produces, the richer these folders become. So, when you look at the checkpoint directory, you can actually see what Spark is thinking, what it's planning, and what it has successfully completed. That's why this directory is the physical proof of the reliability of structured streaming. Yes. Now, I'll touch on one last thing and then I'll finish the lesson. Look, when you expand the checkpoint folder here, you see numbers like 0, 1, and so on. This demonstrates the way that Spark structured streaming marks the passage of time using numbers. Spark streaming does not process data as a single uninterrupted block, friends. Instead, it treats each incoming data as a separate micro-batch. These numbers show which micro-batch Spark has processed. For example, when we load the first dataset, Spark processes it as the first micro-batch and creates a record numbered 0 in the checkpoint directory. This is like a note Spark writes to itself. I received the first data, read it, processed it, and wrote the result. Thanks to this information, Spark doesn't have to process the same data over and over again later. When we load the second dataset, since this is new data, Spark starts a second micro-batch. This time, it creates a new record numbered 1 in the checkpoint folder. So Spark is basically saying, I finished the first batch and now I've successfully completed the second batch as well. If a third dataset had been entered, this time we would see a structure numbered 2 in the checkpoint folder. The logic works exactly like this. The first incoming data is 0, the second is 1, and the third is 2. These numbers aren't random, folks. They progress in a completely sequential and deterministic way. For Spark, these numbers answer the question, how far have I progressed? Yes, the most critical point here is this. If Spark stops for any reason, if the cluster shuts down or if the job is restarted, it looks at the checkpoint folder and says, the last batch I completed successfully was batch number 1. So don't process 0 and 1 again, continue from 2. So these 0, 1, 2 structures under the checkpoint directory are Spark's memory, insurance, and roadmap. These are not the data itself, friends. They are records that show where the data processing left off. Yes, we can't open and read these files under the checkpoint folder. We can't manually examine their contents. In fact, we really shouldn't do this. These files are generated by Spark structured streaming for machines. So they're for Spark's own internal working logic. Dear friends, their contents are not in a format that humans can read. They contain binary formats, internal metadata, and Spark-specific state information.
