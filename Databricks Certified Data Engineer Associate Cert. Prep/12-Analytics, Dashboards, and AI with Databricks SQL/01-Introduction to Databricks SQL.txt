So what is Databricks SQL? Dear friends, Databricks SQL is not a new SQL query language developed by Databricks. The SQL used here is the standard SQL we all know. But what makes Databricks SQL important is not so much the query language itself, but the environment in which the query runs. Databricks SQL retrieves data stored in the data lake, friends, and it makes them queryable using a data warehouse logic. In other words, it allows us to run analytical queries on the existing lake house structure without moving, copying, or remodeling the data to another system. In this respect, Databricks SQL is not just a bridge between the data lake and the data warehouse, but rather a platform that combines the two. To use an analogy, friends, the data lake is like a huge warehouse. Databricks SQL, on the other hand, is like a showroom set up in front of this warehouse with organized shelves, everything labeled, and a space where customers can easily walk around. The data is now prepared. Now, we're going to learn how to present and explain it properly. Alright, let's continue everyone. So, why was Databricks SQL designed as a separate area? Friends, we can answer this question like this. Databricks SQL has been deliberately positioned as a separate area within Databricks. The main reason for this is to separate workloads. When data processing and data analysis use the same resources, performance and cost issues arise. Notebooks are generally used for heavy transformations, ETL processes, and batch operations. By way of contrast, Databricks SQL is specifically engineered and optimized for read-heavy, fast-response, and multi-user analytical queries. This is precisely the reason why Databricks SQL has its own unique compute structure, which is known as a SQL warehouse. Friends, you can also think of it like city traffic. What happens if trucks, passenger cars, and trams all use the same road? Traffic gets jammed. Databricks SQL eases the system by moving analytical traffic into a separate lane. Now, let's talk a bit about the logic behind SQL warehouse. Friends, in Databricks SQL, queries don't run on classic Databricks clusters. Instead, they are executed on SQL warehouses. These warehouses are specifically optimized for BI and SQL workloads. They are suitable for multiple users running queries at the same time and provide stable performance for dashboards. SQL warehouses generally come in two forms, serverless and pro-design. Serverless warehouses are managed by Databricks, and they spin up very quickly, friends. Pro-design warehouses, on the other hand, run on your own cloud infrastructure and offer more control. As a data engineer, it's more important to understand how this infrastructure works than the SQL you write here. Choosing the right warehouse, cost control, and performance optimization are your responsibilities. Alright, let's move on to another question. Who is Databricks SQL used for? Friends, Databricks SQL is not a tool designed for just one role. On the contrary, it allows different roles to come together over the same data. Analysts perform their daily analyses, business units look at dashboards, and data scientists run quick exploratory queries. And data engineers ensure that this entire structure runs smoothly. In this sense, friends, Databricks SQL is the gateway where data transitions from the technical world to the business world. If this gateway isn't designed properly, no matter how high quality the data produced is, it won't generate value. In short, the purpose of this lesson is not to teach you SQL. Things like SELECT, JOIN, or GROUP BY are already familiar concepts. The aim of this lesson is to properly position Databricks SQL within the Databricks ecosystem.
